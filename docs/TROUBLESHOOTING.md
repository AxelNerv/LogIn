# Справка logIn: работа и устранение неполадок

Начните с симптома, затем проверьте соответствующий блок в **Службы → logIn → Диагностика**. Красный результат указывает, где продолжить поиск; сам по себе он ещё не определяет виновника. Перезапуск может временно вернуть связь, но удаляет часть полезных признаков сбоя.

Названия некоторых полей зависят от языка и версии интерфейса. Эта справка описывает текущий код проекта; отдельные возможности могут отсутствовать в старом установленном пакете.

<a id="traffic"></a>

## Как проходит трафик

Обычная цепочка: **устройство → DNS роутера → правило logIn → выбранная секция → сайт**.

logIn связывает настройки, списки, sing-box и движки DPI. sing-box обрабатывает DNS и маршрутизацию. Zapret, Zapret2 и ByeDPI применяются только там, где выбран соответствующий способ обхода и установлен нужный компонент.

У секции есть условия: домены, IP/подсети, готовые списки, устройства и другие ограничения. Порядок имеет значение: более раннее подходящее правило может перехватить трафик до нужной секции. Учитываются также действие и дополнительные условия правила.

- **Прямой выход / обход секции:** соединение идёт через провайдера без VPN. Само по себе это не обходит блокировки.
- **DPI:** пакеты обрабатываются выбранным движком и выходят через провайдера. Выходной IP обычно остаётся вашим; DPI-стратегия не шифрует весь трафик и не гарантирует работу на любом провайдере.
- **Подключение / прокси / VPN:** совпавший трафик уходит через выбранный сервер или VPN-интерфейс. Доступность и задержка зависят также от этого сервера и маршрута до него.
- **Блокировка:** совпавшее соединение отклоняется.

При FakeIP sing-box выдаёт устройству служебный IP и сохраняет связь с доменом. Этот адрес не является настоящим IP сайта. Чтобы доменные правила работали предсказуемо, DNS-запросы устройства должны попадать в нужную цепочку logIn. Сторонний DNS, браузерный DoH или VPN на устройстве могут изменить эту цепочку.

Уже открытое TCP-соединение не переносится на новый выход после добавления домена. Сайт также может помнить IP в своей сессии. После применения правила откройте новое соединение; при необходимости перезапустите только соответствующее приложение. Не начинайте с очистки всех cookies или перезагрузки роутера.

## Для чего нужны вкладки

| Вкладка                   | Что в ней настраивается или показывается                                                                                                                                                                                                                        |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Секции**                | Куда направлять трафик: условия, порядок правил, подключение, подписка, DPI или прямой выход. Удалённые VPN-ссылки обычно добавляются здесь.                                                                                                                    |
| **Серверы**               | Входящие подключения **к самому роутеру**. Например, телефон подключается к Cudy по VLESS или Hysteria2, а роутер обрабатывает его трафик. Есть параметры прослушивания, доступа, ссылки/QR и режим маршрутизации. Набор протоколов зависит от сборки sing-box. |
| **Настройки**             | Общие параметры: DNS, Bootstrap, резервирование, путь DNS, загрузка и другие настройки службы.                                                                                                                                                                  |
| **Диагностика**           | Ручные проверки, состояние компонентов, логи и сведения для поиска причины сбоя.                                                                                                                                                                                |
| **Информационная панель** | Трафик, соединения, состояние службы и серверы активной конфигурации. Проверка задержки не заменяет проверку UDP-голоса.                                                                                                                                        |
| **Мониторинг**            | Наблюдение за работой и соединениями. Доступные сведения зависят от версии и возможностей ядра.                                                                                                                                                                 |
| **Компоненты**            | Установка и обновление logIn, sing-box и движков DPI. Успешное обновление файла ещё не подтверждает работу конкретного сайта.                                                                                                                                   |

### Входящие серверы

Пример: **телефон → сервер на роутере → правила logIn → интернет**. Для входящего трафика можно выбрать правила, прямой выход или конкретную секцию.

Для обычного обслуживания домашних LAN/Wi-Fi устройств создавать входящий сервер не требуется. Для подключения извне адрес и порт роутера должны быть доступны клиенту: учитывайте firewall, NAT терминала и возможный NAT провайдера. Создание записи во вкладке не доказывает доступность извне. Tailscale, если поддерживается сборкой, имеет отдельную схему подключения и проверки.

Не открывайте веб-интерфейс LuCI в интернет для работы входящего прокси. Порт LuCI и порт созданного сервера — разные службы.

<a id="dns"></a>

## DNS, Bootstrap и резервирование

**Основной DNS** разрешает имена сайтов. **Bootstrap DNS** помогает разрешать имена DNS-серверов и серверов подключения и используется отдельными служебными маршрутами. Это два назначения, а не одна общая очередь адресов.

Включённые **DNS-запросы через секцию** отправляют основные запросы через выбранное подключение. Если оно перестало работать, смена основного DNS не починит сам VPN. Bootstrap должен оставаться доступным без зависимости от этого же неработающего подключения.

Поддерживаются UDP, DoH, DoT, DoQ и HTTP/3 при наличии соответствующих возможностей ядра. Схема URL отдельной записи может переопределить общий тип DNS. Обычный UDP не шифрует DNS; защищённые пресеты используют проверку TLS. В пресетах с `?address=…` IP закреплён для подключения, а имя используется для проверки сертификата: разрешать имя самого резолвера заранее не нужно.

### Как выбирается резерв

В списках основного и Bootstrap DNS важен порядок. Служба проверяет активный вариант и выбирает доступный резерв при подтверждённом отказе. Возврат к более приоритетному тоже требует успешных проверок и учитывает минимальное время удержания.

Интервал, тайм-аут, число ошибок/успехов и удержание задаются в настройках. Например, при интервале10с и пороге3ошибки переключение занимает десятки секунд, а не происходит мгновенно; время проб и применения добавляется к интервалу. Если все кандидаты недоступны, служба сообщает об этом, а не объявляет резерв рабочим.

Несколько адресов одного оператора могут отказать вместе. Для резерва полезны проверенные из вашей сети разные операторы. Проверяйте конкретный транспорт: недоступный UDP53 не означает, что DoH того же оператора тоже недоступен. Один пропущенный ICMP ping не является проверкой DNS.

<a id="diagnostics"></a>

## Как читать диагностику

Нажмите **«Запустить диагностику»** и дождитесь завершения. Читайте конкретные строки внутри блока, а не только его цвет. Отсутствующий результат или ошибка RPC означают, что проверка не завершилась, а не что компонент исправен. Повторите проверку после устранения найденной причины.

| Блок                                  | Что проверяет                                                                                           | Что проверить при проблеме                                                       |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| **DNS**                               | Активные основной/Bootstrap DNS, разрешение на роутере, связку с dnsmasq и путь основных запросов.      | Доступность конкретного резолвера, выбранную DNS-секцию и DNS устройства.        |
| **Путь соединения**                   | Этапы DNS/HTTPS, доступность IPv4/IPv6, отдельные QUIC/DoQ-пробы, ресурсы и доступные сетевые счётчики. | На каком этапе отказ; совпадает ли проверяемый путь с проблемным приложением.    |
| **Sing-box**                          | Наличие и версию ядра, службу, процесс и нужные слушающие порты.                                        | Логи запуска, конфигурацию, конфликт портов, совместимость ядра.                 |
| **Inbounds / входящие серверы**       | Созданные входы, прослушивание, конфликт портов и настройки адреса/маршрутизации.                       | Параметры вкладки «Серверы» и реальную доступность со стороны клиента.           |
| **Nftables**                          | Правила/марки logIn, возможные конфликты и сведения об offloading.                                      | Другие пакеты маршрутизации и фактический путь трафика.                          |
| **Zapret / Zapret2 / ByeDPI**         | Наличие и состояние установленного движка, его процессов и доступные признаки обработки.                | Выбранный движок, аргументы, файлы стратегии, применяемую секцию.                |
| **Outbounds / исходящие подключения** | Доступность выходов секций по используемой проверкой цели.                                              | Конкретный сервер/подписку, выбранный выход и его поддержку UDP.                 |
| **FakeIP**                            | Ответ на роутере и доступную браузерную проверку цепочки.                                               | DNS устройства/браузера, локальный VPN и доступность самой проверочной страницы. |

Блоки входящих серверов и DPI показываются в зависимости от конфигурации и установленных компонентов. Успешный HTTPS-запрос не доказывает работоспособность голосового UDP, демонстрации Discord или всех сайтов. Недоступная IPv6-проба не означает отказ IPv4. Время передачи TCP прозрачному прокси не равно времени соединения до удалённого сайта.

Диагностику браузерной цепочки удобнее проводить из LAN/Wi-Fi этого роутера. При доступе к LuCI через другой VPN или удалённый вход браузер может использовать другой DNS/маршрут; учитывайте это при чтении FakeIP-проверки.

<a id="errors"></a>

## Частые ошибки и решения

<a id="internet-down"></a>

### Пропал интернет или всё работает медленно

1. Откройте адрес роутера. Если он недоступен, сначала проверьте кабель/Wi-Fi, адрес устройства и шлюз.
2. В OpenWrt проверьте **Сеть → Интерфейсы → WAN**: есть ли адрес и подключение. Зафиксируйте время проблемы.
3. Запустите диагностику DNS и пути соединения. Сравните обычный ресурс и ресурс, который заведомо идёт через вашу VPN-секцию.
4. Посмотрите нагрузку, память и новые ошибки в логах. Высокая скорость в speedtest не исключает потери пакетов, проблемы DNS или отдельного маршрута.

Если отказали и прямой доступ, и VPN, это ещё не доказательство полной блокировки интернета: нужно разделить LAN/WAN, DNS, сервер подключения и ресурсы роутера. Проверьте результат после исправления на тех же целях.

<a id="vpn-path"></a>

### Не работают только ресурсы через VPN

Проверьте, включена ли нужная секция и какой сервер выбран фактически. Если используется подписка, проверьте её срок и последнее успешное обновление. Сравните несколько ресурсов через тот же выход: один HTTP403/404 может быть ответом сайта, а не отказом туннеля.

Если DNS тоже направлен через эту секцию, ошибка DNS может быть следствием отказа подключения. Проверьте Bootstrap и доступность сервера отдельно. Не подменяйте это скрытым прямым выходом: он может поменять внешний IP и видимость трафика.

<a id="stable-start"></a>

### `sing-box did not reach a stable running state after start. Aborted.`

Это итог проверки запуска: ядро не достигло ожидаемого устойчивого состояния. Причину ищите **перед этой строкой** в логах sing-box и logIn.

Проверки через SSH на роутере:

```sh
/etc/init.d/loghorizon status
loghorizon check_sing_box
sing-box check -c /etc/sing-box/config.json
loghorizon check_sing_box_logs
loghorizon check_logs
```

Если в настройках изменён путь конфигурации, используйте его вместо стандартного. Команда `check` проверяет файл, но не запускает службу и не доказывает доступность VPN-сервера.

Типичные причины: некорректный конфиг, неподдерживаемая ядром опция, занятый порт, ошибка сертификата/файла или нехватка ресурсов. Исправьте конкретную первую ошибку и снова проверьте конфиг. Лишь затем применяйте настройки/запускайте службу в подходящий момент. Не переустанавливайте весь logIn по одной итоговой строке.

<a id="dns-unavailable"></a>

### `DNS failover: all configured main DNS servers are unavailable`

Проверка не получила правильных DNS-ответов ни от одного основного кандидата. Это может быть отказ резолверов **или общего пути через VPN**, а не одновременная блокировка всех операторов DNS.

1. В диагностике сравните основной DNS, Bootstrap и состояние выбранной DNS-секции.
2. Проверьте тип и адрес каждой записи. Для Bootstrap с защищённым протоколом используйте готовый пресет с закреплённым IP.
3. Проверьте независимого оператора через тот же путь; прямое подключение проверяйте отдельно.
4. После изменения дождитесь проверок и убедитесь, что активный DNS отвечает. Не считайте наличие четырёх записей доказательством работающего резерва.

Аналогичное сообщение про `bootstrap` относится к списку Bootstrap. Открытый запрос `dig @8.8.8.8 example.com` проверяет UDP53, а не настроенный DoH/DoT/DoQ.

### `context deadline exceeded`, `i/o timeout`, `no recent network activity`

Это истечение срока ожидания. Посмотрите, кто его сообщил: DNS-обмен, TLS, HTTP или транспорт VPN. Запишите время, секцию и повторяемость. Сравните путь соединения и сервер секции. По одному такому сообщению нельзя отличить блокировку, потери, перегрузку или неработающий удалённый сервер.

<a id="remote-list"></a>

### `Failed to download remote domain/IP list …; skipping it until the next successful update`

Не удалось обновить внешний список. Проверьте точный адрес файла, его существование и ответ источника: HTTP404 означает отсутствие файла, HTTP429 — ограничение частоты, HTTP5xx — ошибку сервера/шлюза. Тайм-аут или ошибка TLS требуют проверки соединения и времени роутера.

Если включена загрузка списков через секцию, проверьте именно её. Рабочий last-known-good кэш при неудачном обновлении сохраняется, если он уже был создан и доступен. Для нового источника без кэша правил ещё может не быть. Не удаляйте рабочий кэш ради повторной загрузки.

Исправьте URL/путь загрузки, затем выполните предусмотренное обновление списков. Оно может изменить активные правила — это отдельное действие, не пассивная проверка. После обновления проверьте нужный домен и время успешной загрузки. Готовый `.srs`/`.json` и текстовый список доменов/IP добавляются в предназначенные для них поля.

<a id="subscription"></a>

### `No compatible subscription request profile produced valid proxy entries for rule '…'`

Служба не получила пригодных записей подключения. Возможны неподдерживаемый ответ, пустая/истёкшая подписка, HTML вместо конфигурации или ошибка её загрузки. Смотрите предшествующие сообщения с HTTP-статусом и причиной разбора.

HTTP504/429 не исправляется сменой формата импорта. Уточните состояние ссылки у поставщика, проверьте путь загрузки и повторите обновление после устранения причины. При наличии сохранённого рабочего кэша не удаляйте подписку и кэш без необходимости. URL подписки содержит доступ к серверам: не публикуйте его в issue или скриншоте.

### Удалённый сервер всё ещё виден на панели

Панель показывает активную конфигурацию. Различайте редактирование строки, **«Сохранить»** и **«Применить»**: сохранённая форма может ещё не стать рабочей конфигурацией. Проверьте, завершилось ли применение без ошибки и не идёт ли обновление подписки. Обновление страницы само по себе не применяет настройки.

Если применение завершилось успешно, но старый сервер остаётся, сохраните время, имя секции и сведения о задании для отчёта. Не очищайте весь конфиг. Проблемы с кнопками/шириной интерфейса сначала сравните с установленной версией LuCI-приложения и обновлением страницы.

<a id="dpi-preset"></a>

### «Не удалось применить выбранный DPI-пресет»

Это ошибка выбора в редакторе: интерфейс не нашёл подходящий пресет или не смог скопировать его стратегию в поле. На этом этапе движок ещё не запускается.

Проверьте соответствие пресета выбранному движку и наличие поля стратегии. Сохраните свой черновик перед обновлением страницы; проверьте актуальность LuCI-приложения, загрузку каталога пресетов и работу редактора в вашей теме. Если стратегия появилась в поле, этап выбора прошёл успешно. Сохранение/применение и проверка движком выполняются отдельно.

### Стратегия не проходит проверку или движок не запускается

Смотрите конкретную причину в результате проверки/применения и логах. Проверьте:

- установлен ли **выбранный** движок и поддерживает ли он аргументы стратегии;
- нет ли ошибки внутренней проверки или `--dry-run`;
- существуют ли файлы fake-пакетов по указанным путям;
- не перепутаны ли стратегия Zapret/nfqws и Zapret2/nfqws2.

Исправляйте первый указанный конфликт. Не переносите Windows-пути и параметры другого движка в роутерный пресет. Даже принятая движком стратегия требует проверки на вашем провайдере: проверка синтаксиса не доказывает обход. Сравнительный BlockCheck может временно менять стратегию; запускайте его отдельно от важного звонка/игры.

### Движок работает, но DPI не помогает

Проверьте, попадает ли нужный поток в DPI-секцию, её домены/IP, протокол и порты. Наличие процесса не доказывает обработку этого соединения. У Zapret учитывайте счётчики нужной NFQUEUE и логи; у других движков признаки могут отличаться.

Не отключайте offloading глобально по одному предупреждению: сначала установите, влияет ли он на фактический путь пакетов. Стратегия, работающая для HTTPS, может не помогать голосовому UDP. VPN/ExitLag на устройстве способен скрыть неработающий DPI во время проверки.

<a id="domain-rule"></a>

### Домен добавлен, а сайт открывается напрямую или не работает

1. Убедитесь, что секция включена, имеет нужное действие и изменения применились.
2. Проверьте приоритет: более ранняя секция может уже перехватывать запрос.
3. Для домена и поддоменов используйте, например, `example.com`; `full:` — точное совпадение, `keyword:` — совпадение по слову, `regex:` — регулярное выражение. Не добавляйте всю подсеть CDN ради одного сайта без проверки последствий.
4. У сайта могут быть отдельные домены входа, API, картинок/CDN. Правило главного домена не покрывает посторонний домен автоматически. Соединению по IP может понадобиться IP-правило.
5. Проверьте DNS клиента, сторонний VPN/ExitLag и откройте новое соединение приложения.

В редакторе секции используйте **«Проверить маршрут правила»** с проблемным доменом. Эта проверка сопоставляет путь HTTPS/TCP с конфигурацией; она не доказывает такой же маршрут голосового UDP. Проверка должна подтвердить выбранную секцию/выход, затем проверьте сам сайт.

HTTP403 или оформленная сайтом страница404 — уже ответ сервера. Он может зависеть от пути, IP/региона, учётной записи или URL. Сравните один и тот же адрес через фактически разные выходы; по виду страницы не определяйте внешний IP.

<a id="one-device"></a>

### Не работает только одно устройство или браузер

Проверьте подключение к нужному роутеру, адрес шлюза и DNS, полученные устройством. Сравните мобильную сеть и Wi-Fi, системный VPN, ExitLag, Private DNS/«Частный DNS» телефона и «Безопасный DNS» браузера. Для сравнения временно используйте DNS роутера и отключите сторонний обход на этом устройстве, затем повторите **тот же** запрос.

Если на роутере FakeIP работает, а браузерная проверка не проходит, возможен обход DNS роутера или недоступность самой проверочной страницы. Не меняйте все DNS роутера до проверки клиента. Возвращайте настройки устройства осознанно: внешний DoH снова может изменить работу доменных правил.

<a id="dns-section"></a>

### «DNS-запросы через секцию содержит недопустимое значение» / «Ожидается непустое значение»

При включённом направлении DNS через секцию нужно выбрать существующую, включённую секцию с поддерживаемым действием и доступным компонентом. Для DNS через VPN выбирайте секцию соответствующего подключения. После удаления/переименования секции старая ссылка может перестать быть действительной.

Проверьте список секций и их действия, заново выберите рабочую секцию в настройках DNS и сохраните. Если список пуст при наличии подходящих секций, зафиксируйте версию интерфейса, ошибку и скриншот; проверьте загрузку страницы и доступность UCI/RPC в диагностике. Не сбрасывайте конфиг.

Отключение DNS-detour — изменение маршрута и приватности DNS, а не универсальный ремонт формы. Если это сделано временно, проверьте, куда теперь уходят запросы, и восстановите нужный режим после исправления.

<a id="discord"></a>

### Discord: Starting, 5000 мс, нет звука или ошибка 2007

Проверяйте отдельно три потока:

| Симптом                                     | Что сравнить                                                                                                                            |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Starting или загрузка меню                  | DNS, HTTPS/API, Gateway/WebSocket, домены обновления и CDN.                                                                             |
| Меню работает, голос не соединяется/5000 мс | Управляющее соединение голоса и медиатрафик UDP, фактическую секцию/порты и ответы в обе стороны.                                       |
| Голос есть, демонстрация не работает/2007   | Отдельное соединение демонстрации, маршрут её медиа и поведение клиента. Ошибка2007 сама по себе не доказывает одну конкретную причину. |

Запишите время, направление проблемы («меня не слышат»/«я не слышу», чей стрим) и состояние ExitLag/VPN. Для проверки DPI убедитесь, что сторонний туннель не обрабатывает Discord. Один удачный запуск или HTTP200 не подтверждает исправность голоса и демонстрации.

После изменения стратегии можно переподключиться к каналу в согласованный момент. Оставьте голос и демонстрацию на10–20минут: проверьте звук в обе стороны, повторные подключения и наличие скачков/обрывов. Ноль исходящих потерь в интерфейсе Discord не исключает проблем приёма или управления соединением. Высокий DNS RTT не равен пингу голоса.

<a id="tls"></a>

### Ошибка сертификата, `x509`, `certificate verify failed`

Проверьте дату/время роутера, имя сервера/SNI, срок сертификата и доверенную цепочку. Для закреплённого ключа проверьте pin через доверенный источник; после смены сертификата он мог измениться. Не выключайте проверку TLS и не берите новый pin из непроверенного соединения как способ скрыть ошибку.

<a id="report"></a>

## Как собрать сведения для помощи

Укажите модель роутера/OpenWrt, версии logIn и sing-box, точное время сбоя, устройство, ресурс, нужный маршрут и последнее изменение. Отдельно напишите, работает ли WAN/обычный сайт, меню/голос/демонстрация Discord и включён ли сторонний VPN.

Ниже команды **для SSH-терминала роутера**. Они проверяют состояние или выполняют сетевые пробы без рестарта служб; проба пути также сохраняет локальную историю диагностики.

```sh
date
/etc/init.d/loghorizon status
loghorizon show_version
loghorizon show_sing_box_version
loghorizon check_dns_available
loghorizon check_sing_box
loghorizon check_connectivity_path
```

Дополнительно можно получить общий отчёт с маскированием конфигов:

```sh
loghorizon global_check masked > /tmp/loghorizon-report.txt
```

Логи службы и ядра:

```sh
loghorizon check_logs
loghorizon check_sing_box_logs
```

Если проблема в DPI, локальный лог соответствующей секции обычно находится в `/var/run/loghorizon/zapret/log/SECTION.log`, `/var/run/loghorizon/zapret2/log/SECTION.log` или `/var/run/loghorizon/byedpi/log/SECTION.log`. Замените `SECTION` внутренним именем секции. Не отправляйте каталог целиком: другие runtime-файлы и кэши могут содержать данные доступа.

Перед отправкой просмотрите **весь** отчёт, логи и скриншоты. Маскирование конфигурации не гарантирует скрытие произвольных секретов в строках логов. Уберите URL подписок/их токены, UUID, пароли, private keys, заголовки авторизации и личные адреса, если они не нужны для разбора. Полные `uci show`, `/etc/config/loghorizon`, JSON sing-box и режим `raw` публично не выкладывайте.

Очищенную историю ручных проверок можно получить командой `loghorizon get_connectivity_history`. Это снимки проверок, а не непрерывная запись всех обрывов; старое успешное измерение не описывает текущий сбой.

Для обращения используйте [issues проекта](https://github.com/AxelNerv/LogIn/issues). Если источник подписки недоступен, передавайте его полный адрес только владельцу сервиса по приватному каналу.

<a id="restart"></a>

## Когда нужен перезапуск

Чтение логов, обычная диагностика и открытие справки не требуют перезагрузки роутера. Сохранение/применение настроек, обновление компонента, запуск BlockCheck и сброс FakeIP — другие действия: они могут изменить активную обработку и прервать соединения.

Перед применением сохраните причину ошибки и убедитесь, что есть доступ к настройкам для отката. Во время важного звонка/игры сначала соберите сведения без изменений. `reset_fakeip` очищает состояние и перезапускает обработку; не используйте его как универсальный первый шаг.

Перезапускать только сломанный компонент стоит после установления причины, если исправлению требуется повторный запуск. Восстановление интернета после рестарта ещё не доказывает устранение первопричины.
